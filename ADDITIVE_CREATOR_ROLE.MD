FULL CURSOR PROMPT — Additive Creator Role Upgrade ("Switch to Creator")
Important — check existing code first: Before building anything, inspect the existing user role/permission system, specifically how Audio Lover (non-creator) and creator roles are currently distinguished in the data model, and how existing role-based UI rendering works (e.g. how the app currently decides whether to show a creator's feed screen versus an Audio Lover's feed screen). Also inspect the existing account onboarding flow, and the fan engagement tracking and referral link system (tipping history, referral records, engagement/supporter status) already built for Audio Lover accounts.
Critical design requirement, do not deviate from this: This must be implemented as an additive role change, not an account type switch or reassignment. The user's existing Audio Lover role, and all data tied to it (tipping history, referral link, referral tracking records, engagement/supporter status), must remain fully intact and untouched. The account gains an additional creator role/permission alongside the existing Audio Lover role, it does not replace or overwrite it. If the current data model only supports a single, exclusive role per user (e.g. a single role field with one value), this prompt requires changing that to support multiple simultaneous roles per user (e.g. a roles array, or separate boolean/permission flags such as is_audio_lover and is_creator), do not force this into a single-value field that would require destructive reassignment.
What to build:
Part A, entry point:
Add a clearly visible, easily discoverable "Become a Creator" (or "Switch to Creator," user-facing language can differ from the internal additive mechanism) option, placed prominently in account settings and/or on the user's own profile screen, not buried in a submenu.
Part B, creator upgrade onboarding flow:
Tapping this option launches a short, dedicated onboarding flow to collect creator-specific profile information not already present on the Audio Lover account (e.g. artist/stage name, genre or category, any other fields required for a creator profile per the existing creator onboarding flow, reuse those same fields and validation rather than inventing new ones). This should be shorter than the full original account onboarding, since the user already has an established account and existing profile data that shouldn't need re-entering.
Part C, role and data update:
On completion, update the user's role/permission data to add creator status, following the additive approach specified above. Ensure this change is reflected consistently across both the mobile app and web app. Verify, as part of this build, that the following existing Audio Lover data remains fully accessible and unaffected after the upgrade: tipping history, referral link and referral tracking records, and engagement/supporter status data.
Part D, post-upgrade experience:
Once upgraded, the user should now have access to creator-specific screens, features, and navigation (the existing creator feed/profile experience), while retaining full access to their Audio Lover history and data (e.g. their past tips given, their existing referral link should continue working and tracking as before).
Scope boundaries:
Do not build a reverse flow (creator downgrading back to Audio Lover only) as part of this prompt, that is separate, undecided future work
Do not modify or remove any existing Audio Lover functionality as part of this change, the goal is addition, not replacement
If the current data model requires non-trivial restructuring to support multiple simultaneous roles, flag this clearly rather than forcing a fragile workaround, this may be a larger schema change than a simple flag addition depending on how the existing system was built
General rules:
Follow existing code style, onboarding flow patterns, and role-based rendering conventions throughout
Test thoroughly that existing Audio Lover data integrity is preserved after upgrade, this is the single most important requirement of this entire prompt
